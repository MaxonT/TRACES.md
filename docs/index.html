Every AI agent should leave a record of what it actually did.

AGENTS.md tells an agent how to behave in a repo. TRACES.md tells it how to leave an objective, append-only record of what it did: which tool, what it did, how it ended. Failures included. One plain file per task, readable by people and parseable by scripts.

TRACES.mdobjective process record for AI agents

An agent says "done, tests pass". Did it run the tests? Which command? Did the first run fail? What did it try next? Today that lives in a chat window that scrolls away, in a format that differs per tool. You cannot improve what you cannot replay.

The format, at a glance

Save it as .trace/2026-10-12-claude-code-fix-date-parser.md. Each step is one line: ts | tool | action | result.

task: Fix the failing date parser test
agent: claude-code
started: 2026-10-12T09:14:02-05:00
spec: traces/0.1.0
repo: acme/billing
branch: fix/date-parser

2026-10-12T09:14:05-05:00 | shell: git status | list working tree changes | ok: clean
2026-10-12T09:14:31-05:00 | shell: python -m pytest tests/test_dates.py | run the date tests | fail: exit 1, 1 failed, 11 passed
2026-10-12T09:14:48-05:00 | read: src/dates.py | read the date parser | ok: 64 lines
2026-10-12T09:15:02-05:00 | edit: src/dates.py | change the parse format string to %Y-%m-%d | ok: 1 line changed
2026-10-12T09:15:20-05:00 | shell: python -m pytest tests/test_dates.py | run the date tests | ok: exit 0, 12 passed
2026-10-12T09:15:41-05:00 | shell: python -m pytest | run the full test suite | partial: exit 0, 212 passed, 3 skipped

The same trace has a machine form, JSONL, one JSON object per line, with a published JSON Schema. The two forms convert into each other without loss (traces fmt --to jsonl).

{"type":"step","ts":"2026-10-12T09:14:31-05:00","tool":"shell: python -m pytest tests/test_dates.py","action":"run the date tests","result":{"status":"fail","detail":"exit 1, 1 failed, 11 passed"}}

Four fields

When, which tool, what it did, result. Result is ok, fail or partial, plus a short factual detail.

Append-only

A step is never edited or deleted. A mistake is fixed by a later step. History stays replayable.

Objective only

No reasoning, no opinion, no story. What happened, not what the agent said about it.

Greppable

grep '| fail' .trace/* is already error analysis. No database, no daemon, no account.

Why every AI should write traces

Error analysis

Which tools fail, for which agents, how often, after which steps. The failed steps in order with the exact command and the exact outcome.

Self-optimization

An agent that can read its own failure history can stop repeating the same mistake. A trace is the training signal you already produce and throw away.

One format for every tool

Cursor, Trae, Kiro, Claude Code, Codex, Aider: all can emit the same lines. Compare agents on the same task, across vendors.

Accountability

Reviewers see what was run, not a summary of what went well. A diff tells you what changed; a trace tells you how it got there.

Separates fact from story

The final answer is prose. The trace is the record. Keeping them apart is what makes the record trustworthy.

Costs almost nothing

One line per operation. No dependency. A trace is a file you can commit next to the work it describes.

The record is sacred: failures are recorded.

A trace that lists only the successes is worse than none, because it looks like evidence. The spec makes this a rule, and the validator enforces it where it can see an omission: a step marked ok next to a non-zero exit code, or a retry whose failure was never recorded, is rejected.

$ traces validate examples/invalid/2026-10-12-demo-hidden-failure.md
examples/invalid/2026-10-12-demo-hidden-failure.md:6: error[E040]: hidden failure: status is ok but the result reports exit code 2; record it as 'fail'
INVALID: 1 files, 1 errors, 0 warnings
$ echo $?
1

The reference CLI

Python 3.9+, standard library only, MIT. One command, traces.

CommandWhat it does
traces initcreate .trace/ and a trace file for today
traces newstart a trace for a task (reads repo, branch, sha from git)
traces appendadd one step: locked, checked, atomic. Refuses a dishonest or out-of-order step
traces run -- cmdrun a command and record it with its real exit code, timeouts and missing commands as fail
traces validatelint a file or folder against the spec; exit 1 on any error (a CI gate)
traces show, catrender a trace for reading; print it in either form
traces fmtnormalize, and convert between Markdown and JSONL
traces statsper agent, per tool, failure rate, most failing commands (--json)
traces statushealth of a trace folder with alert thresholds for CI (--check)
$ traces stats examples/*.md

Install

Give it to your AI. Paste this into any agent that can run shell commands. It reads the install page, asks before it changes anything, and starts writing traces:

Read https://maxont.github.io/traces-md/install and install traces for me.

Terminal shortcut (never edits your shell config; add --dry-run to preview):

curl -fsSL https://maxont.github.io/traces-md/install.sh | bash

Or run the container: docker run --rm ghcr.io/maxont/traces --help. Full instructions for humans and for your AI: /install.

Not this

Not a logging framework, not telemetry, not analytics with a backend. No daemon, no server, no account: a trace is a file. It does not record why an agent did something. Reasoning belongs elsewhere.
